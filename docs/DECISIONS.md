# Decisions

Format: ADR-NNN — decision, reason. Add a new entry (do not rewrite history) when architecture changes; an entry that replaces an older one says which. Entries marked *(planned)* are decided but not implemented yet.

## Platform and tooling

- **ADR-001 Monorepo, `apps/api` + `apps/web`.** One repo, pnpm workspace for the web app, independent Go module (`factual/apps/api`) for the API.
- **ADR-002 Self-hosted, server-authoritative.** One Go API and one PostgreSQL database are the single source of truth. No local-first/CRDT sync as in Actual Budget: expense splitting writes into several users' ledgers at once, which needs one consistent store. Offline use is out of scope.
- **ADR-003 PostgreSQL 15+.** The schema relies on deferred constraint triggers, `unique nulls not distinct` and `on delete set null (column)`. Local development and integration tests run PostgreSQL 18 from `docker-compose.yml`.
- **ADR-004 echo v4, spec-first OpenAPI with oapi-codegen (strict server).** `apps/api/api/openapi.yaml` is the source of truth; handlers implement the generated interface; requests are validated by echo-middleware. `skip-prune` keeps shared schemas (the `Error` envelope) that no operation references yet.
- **ADR-005 Web API types are generated from the same spec.** openapi-typescript writes `apps/web/src/lib/api.gen.ts`; calls go through openapi-fetch and its TanStack Query bindings (`api` / `$api` in `src/lib/api.ts`). No hand-written response types.
- **ADR-006 sqlc on pgx/v5, one private package per domain.** A domain's SQL in `internal/domain/<name>/queries/*.sql` is generated into `internal/domain/<name>/internal/db`, which no other package can import. `uuid` maps to `google/uuid`, `timestamptz` to `time.Time`.
- **ADR-007 goose SQL migrations, embedded and applied on startup.** Migrations in `apps/api/db/migrations` are compiled into the binary and run when the API starts (`FACTUAL_DB_AUTO_MIGRATE`, default on), so a self-hosted install needs no separate migration tool. sqlc reads the same directory as its schema. Atlas (used in the go-admin template) was rejected: the schema needs triggers and functions, which Atlas only diffs in its paid edition.
- **ADR-008 Configuration is environment variables only (`FACTUAL_*`).** Few settings, and env vars are what self-hosted deployments (containers, systemd) use. Local development values live in `apps/api/mise.toml`; personal overrides in a git-ignored `mise.local.toml`. No config files, no koanf.
- **ADR-009 mise for tools and tasks, dekit for the dev stack, lefthook for hooks.** mise pins every tool version and holds all tasks (monorepo mode: `//apps/api:<task>`, `//apps/web:<task>`). `mise run dev` opens dekit (`dekit.yaml`: db, API with air, web). Git hooks are the tracked `.githooks/pre-commit`, which runs lefthook; `mise run setup` enables it through `core.hooksPath`.
- **ADR-010 TanStack Start (React) in SPA mode.** Chosen over Nuxt. Both were viable and the performance difference is not noticeable for this app (a virtualized grid renders a few hundred cells); the reasons are typed, validated URL search params for ledger state (month, account, filters) and first-class React support in TanStack Table/Virtual/Query. The React Compiler is enabled. The app sits behind a login and all data comes from the Go API, so the build is a static SPA (`dist/client`, entry `_shell.html`); server functions and SSR are not used.
- **ADR-011 oxlint and oxfmt, extending the TanStack shared configs.** `@tanstack/oxlint-config` (type-aware, needs `oxlint-tsgolint`) and `@tanstack/oxfmt-config` replace the ESLint + Prettier toolchain the scaffold came with. The shared lint config is framework-agnostic, so `oxlint.config.ts` adds the React plugin (hooks rules, `jsx-key`). Formatting follows the TanStack config, not the go-admin template's.
- **ADR-012 Go is linted and formatted with golangci-lint** (standard linters, goimports), generated code excluded.
- **ADR-013 UI text is Traditional Chinese (zh-TW)**, written directly in components. Code, identifiers and API error codes are English.

## Users and access

- **ADR-014 Built-in accounts with server-side sessions.** Username + password (argon2id), sessions stored in PostgreSQL and referenced by an HttpOnly cookie; only the hash of the session token is stored. OIDC login may be added later as an option.
- **ADR-015 Invite-only registration; the first user is the instance admin.** *(planned)* Fits a self-hosted instance shared with friends. Everyone a user can split with is an account on the same instance; there is no federation.
- **ADR-016 Placeholder members are `users` rows without a password.** A friend who has not registered yet can already take part in shared expenses. They register through an invite that claims that row (`invites.claims_user_id`), so nothing has to be merged afterwards.
- **ADR-017 Authorization is plain Go, no casbin.** Roles are few and fixed (budget: owner/editor/viewer; group: admin/member), so a typed role -> permission map behind one `Can()` function and one middleware is enough and is checked by the compiler. What is actually hard here (list filtering, visibility of shared expenses, "only the recorder may edit", privacy between participants) is data relationships, solved by SQL scoping and table structure, which a policy engine does not help with. Revisit if permissions must become configurable at runtime.
- **ADR-018 A budget can have several members, but v1 ships personal budgets plus splitting.** `budget_members` with roles exists so shared budgets (e.g. a couple) need no schema change later. Splitting happens between users, not budgets: each user names a default budget (`users.default_budget_id`) that receives their side of a shared expense.
- **ADR-019 Tenant isolation is enforced in the database.** Every table inside a budget carries `budget_id` and references its parents with composite foreign keys `(budget_id, id)`, so a row can never point at another budget's account, category, payee or transaction.

## Ledger and budgeting

- **ADR-020 Money is `bigint` minor units.** No floating point. An entry's amount is the change in its account's balance: positive increases it, negative decreases it. Liability accounts (credit cards, loans, money owed to friends) have negative balances.
- **ADR-021 Primary keys are UUIDs the client may generate.** `:w` commits a batch in which new rows reference each other (a transfer's two sides, a split and its transaction) and may be retried; client-side ids (UUIDv7 recommended) make that possible without a round trip.
- **ADR-022 A transaction is a header plus entries `(account, category?, amount)`.** One row in the editor is the entries of one transaction on the account being viewed. A plain expense is one entry; a split is several entries on the same account; a transfer is two entries without a category.
- **ADR-023 The ledger invariant follows cash, not net worth.** Per transaction, entries without a category on on-budget accounts must sum to zero, and entries on off-budget accounts never carry a category. A deferred constraint trigger checks this at commit. It guarantees *on-budget account total = pool + all envelope balances*. Pure zero-sum double entry was considered and rejected: paying loan principal is not an expense there, but the cash is gone, so envelopes would stop matching the money available. Moving money to an off-budget account therefore always needs a category.
- **ADR-024 Accounts are on-budget or off-budget.** Cash, bank, credit card, friend/group and suspense accounts are on-budget; loans and investments are off-budget (tracked for net worth only). The flag cannot change once an account has entries.
- **ADR-025 Income goes to a pool, not to a month.** Entries with an income category feed a timeless pool; the user decides how much to move into each envelope per month (`allocations`, one row per category and month). Unlike Actual Budget, income does not become "to budget" for the month it arrives in, so irregular income does not inflate a month, and the pool shows the remaining runway.
- **ADR-026 Envelope balances are cumulative sums; there is no month close.** Balance = allocations to date + activity to date, carried forward whether positive or negative. Nothing is stored per month besides the allocation itself. A cache table may be added if sums become slow.
- **ADR-027 Categories form a tree of at most three levels.** Budgets sit on leaves by default and parents show totals; a parent with `pooled = true` owns one envelope shared by its children. Names are unique within a parent and cannot contain `/`, which is the path separator in the editor (`交通/加油`).
- **ADR-028 Credit cards are on-budget accounts with a negative balance.** Spending on a card lowers the envelope and raises the debt in the same entry, so the money to pay the card is always set aside. The "reserve" shown for a card is derived from its balance, never stored, so it cannot drift.
- **ADR-029 Credit card statements are first-class.** A statement has a period, due date and amount due; entries record which statement bills them and which statement a payment settles. Paying a card is a transfer linked to a statement, which lets the app show what is due, what is covered and what is missing.
- **ADR-030 Instalments are schedules in v1.** A purchase paid in N instalments is a schedule with N occurrences, so the envelope is charged each period. Charging the envelope once while billing over several statements needs one entry spread across statements and is deferred.
- **ADR-031 A savings goal attaches to a category.** The amount saved is that category's envelope balance; progress and estimated completion are derived. Kinds: target amount, target amount by a date, maintain a level (N months of average spending, for an emergency fund), fixed monthly amount.
- **ADR-032 Loans are off-budget accounts; the amortization schedule is computed, not stored.** A loan keeps principal, term, method (annuity or equal principal), grace period and its rate periods (`loan_rates`, the first row being the initial rate). Each payment is generated by a schedule and split into a principal entry (a categorized outflow plus the matching reduction of the loan account) and an interest entry. Extra principal payments are ordinary entries; the schedule is recomputed from them.
- **ADR-033 Schedules generate transactions directly; nothing is matched.** A schedule is a transaction template plus a recurrence rule. Each generated transaction is unique by `(schedule_id, occurrence_date)`, so reruns never duplicate and no heuristic has to guess which transaction belongs to which occurrence (the opposite of Actual Budget's matching). The rule is stored as an iCalendar RRULE compiled from the editor's DSL, alongside the line the user wrote (`source`) so the editor can show it back. An estimated amount (`~`) produces a transaction marked `needs_review`.

## Splitting

- **ADR-034 A shared expense lives outside any budget.** `shared_expenses` with its payers and shares belongs to the users involved (optionally a group). The database checks at commit that payments and shares each sum to the total. A settlement is a shared expense of kind `settlement`: the payer pays, the receiver's share is the whole amount.
- **ADR-035 Each participant gets exactly one transaction in their own budget.** It is generated from the shared expense and linked to it (`unique (budget_id, shared_expense_id)`). When the recorder edits the expense, amounts are regenerated but the participant's own category and note are kept. Transactions created for someone else arrive marked `needs_review`.
- **ADR-036 Money between people is an on-budget account per friend or per group.** Every participant records their share as a categorized entry on that account; a payer additionally transfers what they paid into it. The balance is then what the user is owed (positive) or owes (negative). Owing a friend works exactly like a credit card: the envelope is charged when the expense happens and repaying is a plain transfer. Money advanced for others is not the payer's expense.
- **ADR-037 A group has one account per member, not one per pair.** The balance is the member's net position in the group, so debt simplification only changes the suggestion of who pays whom and never touches the ledger. Direct splitting between two friends uses one account per friend.
- **ADR-038 A payer who did not record the expense pays from a suspense account.** The recorder cannot know which of the other payer's accounts was used, so that side is posted to the budget's suspense account and marked `needs_review` until its owner picks the real account.
- **ADR-039 Categories are inherited through a hint, then mapped.** The shared expense carries the recorder's category path as text. Each participant's category is chosen in this order: the default category of that friend/group account, the participant's own mapping from that hint (remembered once corrected), a category with the same path, otherwise an inbox category. Changing the category affects only the participant's own budget.
- **ADR-040 Participants see the shared expense, never each other's ledger.** Shared expenses and budget transactions are separate tables and the splitting API only returns the former. The category hint is the one deliberate exception.
- **ADR-041 Budgets have one currency; shared expenses may record a foreign one.** A shared expense is settled in the group's currency and can keep the original currency, amount and the exchange rate at the time. v1 assumes the group's currency equals its members' budget currencies.

## Editor

- **ADR-042 Vim-style editing in two parts.** *(planned)* The transaction grid implements normal-mode navigation and row operations itself (a small state machine); the slash-command draft blocks (`/add`, `/schedule`, ...) are CodeMirror 6 with its Vim extension, with completion sources for payees, categories, accounts, friends and groups.
- **ADR-043 Drafts are saved locally; only `:w` commits.** Unsaved changes survive a crash but nothing reaches the server until the user writes, because a commit can notify other people (splits).
- **ADR-044 `:w` is one atomic batch.** A single endpoint takes every create, update and delete of the buffer, applies them in one database transaction and returns errors per row for the editor to mark. The DSL is parsed in the browser (it is needed there for completion and live validation); the server accepts structured JSON only and validates it again.
- **ADR-045 Grid performance rules.** The grid is virtualized; the cursor is a single overlay element rather than per-cell state; a cell being edited keeps its text locally and writes back on leave; one key listener sits on the grid. These matter more than the choice of framework (ADR-010).

## Login

- **ADR-046 OpenID Connect login, with providers configured in the web app.** The instance admin adds identity providers by issuer URL on a settings page; anything that serves OIDC discovery works, and no config file or restart is involved. The flow is the authorization code flow with PKCE, state and nonce; its state travels in a short-lived encrypted cookie, not in the database. Same design as the go-admin template.
- **ADR-047 An identity logs in only after its owner linked it.** A user logs in with a password, links an identity from their profile, and can use it from then on. Identities are matched by (provider, subject), never by email, and an unknown identity is rejected rather than turned into a new user: an identity provider must not be able to create accounts or take one over through a matching email address. Registering through an invite with an identity instead of a password belongs to the invite feature (ADR-015).
- **ADR-048 Client secrets are encrypted at rest; the key comes from the environment.** `FACTUAL_ENCRYPTION_KEY` (AES-256-GCM) seals identity providers' client secrets and the flow cookie. The API never returns a secret; an empty secret on update keeps the stored one. Without the key OIDC login is unavailable and the settings page says so. Keeping the key in the database was rejected: it would sit next to the secrets it protects.
- **ADR-049 The first admin is created from the environment.** While nobody can log in, startup creates the user in `FACTUAL_BOOTSTRAP_ADMIN_USERNAME`/`_PASSWORD` as instance admin and refuses to start without them. This is the "first user is the instance admin" of ADR-015; a first-run setup page was rejected because whoever reaches a fresh instance first would become its admin.
- **ADR-050 Session cookie and CSRF.** The session token is random, httpOnly, SameSite=Lax and Secure whenever `FACTUAL_PUBLIC_URL` is https; only its SHA-256 is stored. State-changing requests that the browser marks as cross-site (Fetch Metadata) are rejected, which together with SameSite=Lax is the CSRF protection, so no token has to be threaded through the web app. Sessions end after 30 days idle or 90 days in total by default, and all other sessions end when the password changes.
- **ADR-051 Every operation declares `x-auth` in the spec.** `public`, `authenticated` or `admin`; a missing declaration stops the API at startup, so an endpoint cannot be exposed by forgetting a check. This is the instance-level part of ADR-017; budget and group roles will be checked in the domains.
- **ADR-052 shadcn/ui for web components.** Radix primitives with Tailwind, copied into `src/components/ui`. The app is keyboard-driven and will need unusual focus and key handling (the Vim grid, completion menus); owning the component source makes that possible without fighting a library, while forms, dialogs and menus still come ready-made and accessible. Vendored components are excluded from oxlint.

## Visual design

- **ADR-053 A ledger in blue-black ink, dark by default.** The theme is a bookkeeping ledger: blue-black ink and ledger paper as the two grounds (dark and light mode), kraft envelope as the one accent for primary actions, the cursor and focus, the ledger's blue ruling for borders, red for negatives (赤字) and jade for positives. Dark is the default; light is the same ledger on paper; the choice is per browser (next-themes, `localStorage`). Colours are the shadcn CSS variables in `apps/web/src/styles.css` plus `--positive`, `--rule` and `--kraft`; components use the tokens, never raw colours.
- **ADR-054 One typeface with a mono axis.** Recursive (variable, self-hosted via Fontsource) is proportional for the interface and monospaced (`MONO` axis) for figures, identifiers and the editor, so the Vim grid and the rest of the app share letterforms. Chinese falls back to the system's Traditional Chinese face. Amounts use `.amount` (tabular figures; `.amount-negative`, `.amount-positive`).
- **ADR-055 The app is framed like an editor.** A sidebar of places, the page, and a status line along the bottom (section and page, connection, user), which is where editing mode and unsaved changes will show once the grid exists. The block cursor after the wordmark is the product's mark; it blinks only on the login page, where the app waits for input.

## Budget setup

- **ADR-056 TWD is kept in whole 元.** Amounts are integers in a per-currency minor unit (ADR-020); the API returns it with each budget as `minorUnits`. Currencies whose smaller units are not used in practice (TWD, JPY, KRW and a few others) have 0, the rest 2. A budget's currency cannot change after it is created.
- **ADR-057 `x-budget` declares the permission an operation inside a budget needs.** `read`, `write` or `manage`, checked by one middleware against the caller's role (ADR-017) before the handler runs; a path with `{budgetId}` that does not declare it stops the API at startup. A budget the caller is not a member of answers 404, like one that does not exist. Handlers then trust the budget id and scope every query by it. Viewers read, editors also write transactions and allocations, owners also change accounts, categories and members.
- **ADR-058 A user creates their first budget explicitly.** Logging in without a budget opens a setup page (name, currency, a starter set of categories) instead of creating one silently, so the currency is chosen once and on purpose. The first budget a user creates becomes their default (ADR-018).
- **ADR-059 Opening balances are transactions marked `is_opening`.** On an on-budget account the opening balance is recorded in the system income category `opening_balance` (identified by `system_key`, not by name), so it reaches the pool like other money coming in; on a tracking account it has no category. An account whose only transaction is its opening balance can still be deleted, and its opening balance goes with it; once it has other transactions it can only be closed, and only with a zero balance.
- **ADR-060 Categories are archived rather than deleted once used.** Deleting a category is refused while it has subcategories, entries, allocations, schedules or a goal, because allocations and goals would otherwise be deleted with it. Archived categories, and everything under them, are hidden from the category page until asked for.
- **ADR-061 Subcategories share their parent's budget by default.** New expense categories, the starter set included, are created with `pooled = true`, so a budget is set on the top-level category and its subcategories draw from it; turning it off on a parent budgets each subcategory separately. This replaces "budgets sit on leaves by default" in ADR-027. Income categories never pool.
- **ADR-062 The UI says 預算, not 信封.** What the code and these ADRs call an envelope (a category's allocated money and its balance) is shown to users as that category's 預算 (e.g. 共用預算, 還沒分配到預算的錢). The word 信封 does not appear in the interface; the README still names the method 信封式預算.

## Account register

- **ADR-063 A register row is one transaction seen from one account.** Columns follow the order the user writes a line: date, payee, note, category, outflow, inflow, cleared, with the running balance last. Money is entered in separate outflow and inflow columns, as amounts typed without a sign. A row with several entries on the account, or entries on more than two accounts, is a split: its date, payee, note and cleared state are edited in the grid, its category and amount in the split editor (still to come).
- **ADR-064 Transfers are written as `@account` in the payee cell.** The row then stands for two entries, one per account. Its category cell is used only when the transfer crosses between a budget and a tracking account (ADR-023), and then belongs to the budget side, so loan principal is recorded from either account's register. Within the budget, or between tracking accounts, a transfer has no category. Cleared is per entry: clearing a transfer in one register leaves the other side as it was.
- **ADR-065 The batch endpoint replaces whole transactions and reports problems per transaction.** `POST /budgets/{id}/transactions/batch` takes upserts keyed by the client's ids and a list of deletes, validates every transaction against the ledger rules before writing, and answers 422 with problems by transaction id and field when any fail, saving nothing. Payees are sent by name and created on first use; the payees list carries each payee's last category so the editor can fill it in.
- **ADR-066 Running balances follow time, not the screen.** The register shows the newest transactions first and computes balances on the client: by date, then within a day the opening balance, saved rows and unsaved rows, each from the bottom of the screen up. Where `o` puts a new row does not change the balances above it.
- **ADR-067 The editor keeps Vim's names and keys.** Normal mode moves with `hjkl`, `w`/`b`, `gg`/`G`, counts and `Ctrl-d`/`Ctrl-u`; `i`/`a`/`Enter` edit a cell, `c`/`s` replace it; `o`/`O`, `dd`, `yy`/`p`/`P`, `x` (cleared), `u`/`Ctrl-r` and `.` work on rows; `:w`, `:q`, `:q!`, `:wq`, `:e!` and `:<n>` are commands. Insert mode completes payees, `@` accounts and category paths, and Tab walks the editable cells of the row. The status line names the mode as Vim does (NORMAL, INSERT, COMMAND) and counts unsaved rows. Dates accept `t`, `y`, `-1`, `5`, `11/5` and full dates; amounts accept arithmetic.
- **ADR-068 Splits are lines, edited in a window under the register.** A transaction seen from one account is a list of lines: each entry on the account is a line, and each entry on another account pairs with a line of the opposite amount, which becomes a transfer line (a loan payment from the bank is a principal line transferred to the loan plus an interest line). A row with one line is an ordinary row (a category, or `@account`); with several it is a split, and its category and amount cells open the split editor, a window under the register like Vim's `:split` with columns transfer account, category, memo, outflow, inflow. It opens from a split's cells, the category completion "拆分成多個類別…" or `:sp`; `o` adds a line carrying what is left of the amount the row had when the window opened; `q` closes it and applies the lines as one change (`u` undoes it). Empty lines are dropped and a single remaining line turns the row back into an ordinary one. Entries that do not pair up from this account's side (a split written from another account) are shown as a locked row that names the account to edit it in. Drafts moved to version 2; older drafts are dropped.
- **ADR-069 Payees are renamed, merged and deleted on their own page.** Renaming onto another payee's name is refused (`payee_exists`), so that two payees never silently become one; merging moves the transactions and schedules of the sources to the kept payee and deletes the sources in one database transaction. Only a payee nothing uses can be deleted. Editors and owners may do all three (`x-budget: write`); the list carries each payee's transaction count.
- **ADR-070 Key mappings are a vimrc kept on the server.** Each user has one text of mappings (`users.editor_keymap`, `GET/PUT /me/preferences`) so they follow the user to every device. The web app parses it (`apps/web/src/lib/keymap.ts`): `nnoremap`/`nmap`/`noremap`/`map` for normal mode, `inoremap`/`imap` for insert mode, `let mapleader` and `<Leader>`, Vim's key notation; lines it does not understand are skipped and shown on the editor settings page (設定 → 編輯器), which will also hold the editors' other options. Every mapping is non-recursive. Normal mode waits up to a second for a longer mapping as Vim's `timeoutlen` does. Insert mode lets characters type and takes them back when the last ones complete a mapping (`jk` → `<Esc>`), and leaves keys composing Chinese input alone. Keys a mapping produces run one per render, so `:w<CR>` opens the command line, types and runs like typed keys. Command-line mappings are not supported. The CodeMirror 6 slash blocks (M5) use the same parsed mappings: each one is handed to codemirror-vim as a non-recursive mapping in its mode, with `<Leader>` already resolved by our parser, so one vimrc drives both editors.
- **ADR-071 Accounts live in the sidebar, and groups of them have registers.** As in Actual, the sidebar lists 所有帳戶, 預算內 and 追蹤 with their accounts and balances; each opens a register, and a budget opens on 所有帳戶 (until the budget page of M6). A group's register (`GET /budgets/{id}/register?scope=all|onBudget|offBudget`, routes `/accounts/all`, `/accounts/on-budget`, `/accounts/off-budget`) shows one row per transaction and account of the group it has entries on, with an account column; a transfer between two accounts of the group is on two rows. Rows are keyed by transaction and account, and every row of a transaction is rebuilt from the one being edited, so the two sides never disagree; `:w` sends each transaction once and `dd` deletes all its rows. New rows start on the account of the row under the cursor, and the account cell moves a row to another account. Drafts moved to version 3.
- **ADR-072 Moving between panes is Vim's window commands, bound by the user.** Elements marked `data-pane` (the sidebar, the page, the register, the split window) are panes; `<C-w>h/j/k/l` and `:wincmd h` move focus to the pane in that direction that had focus last, back to where focus was in it. Nothing is bound by default, and the browser keeps the real Ctrl-w (it closes the tab), so the commands are reached through the user's mappings, the usual vimrc idiom `nnoremap <C-h> <C-w>h` (ADR-070). Editors (`data-editor`) apply mappings themselves; elsewhere (the sidebar, settings pages) a one-key normal-mode mapping to a window command applies too. Fields, open dialogs and menus keep their keys. In the sidebar j/k move between links and Enter opens one. While the split window is open the register above it only moves; its changes wait until the split is closed.
- **ADR-073 Visual mode selects whole rows.** `V` (and `v`, since a row is the unit) starts Vim's linewise visual mode in the register; motions and counts extend the selection, `o` jumps to its other end, `gv` brings back the last one, and Shift-click selects from the cursor. On a selection `d` deletes, `y` yanks, `x` toggles cleared and `c` opens one cell editor whose text goes into the cursor's column of every selected transaction (Enter applies, even empty; Esc with nothing typed cancels). Operators work per transaction, not per row, so a transfer shown twice is changed once; rows that cannot take the change (deleted, opening balance, a split's amount or category) are skipped and counted in the message. Each operation is one undo step, `.` repeats `d` and `x` over as many rows, and `yy`/`dd`/`x` take counts. Deleting or clearing marks all rows when any is unmarked and unmarks them when all are marked. Visual mode has its own mappings, as in Vim: `vnoremap`/`xnoremap` (`noremap` is normal and visual). No multi-transaction split, and no system clipboard.
- **ADR-074 Keys are listed under `?`; focus is a kraft tint.** The register's hint line keeps only the basics (hjkl, i, o, x, :w) and `?` opens the full key reference, with the user's own mappings, in the register and the split window alike. The register fills its width: payee, note and category share the room beyond their minimum widths (the split window's text columns do the same). Where keyboard focus is shown it is a kraft tint, as a visual selection is, never a ring around a whole region: the register has no focus ring, and its cell cursor dims while focus is elsewhere; a focused sidebar link is tinted while the current one keeps its kraft bar; the completion list's picked option is tinted with a bar and scrolls into view. Ctrl-n cannot be used in Chrome (the browser keeps it for a new window), so completion also takes the arrows, and users map other keys to `<C-n>`/`<C-p>` (`inoremap <C-j> <C-n>`); a completion picked with the keys is kept by Enter and by Esc, even before anything is typed.
- **ADR-075 Mappings can be limited to a pane with `autocmd FileType`.** As Vim users map keys for netrw (`autocmd FileType netrw nmap <buffer> l <CR>`), `autocmd FileType sidebar nnoremap l <CR>` maps `l` only in the sidebar; the file types are the pane names of ADR-072 (`sidebar`, `register`, `split`, `main` for other pages), several separated by commas. Other autocmd events are not supported; `<buffer>` is accepted and changes nothing. In a pane its own mappings win over global ones of the same keys. The sidebar now reads keys through the mappings too (j/k, gg/G, Enter opens a link, `<C-w>` moves), so it is marked `data-editor` and the page-wide layer of ADR-072 is left with pane `main`. - **ADR-078 The budget page shows one month and saves each allocation at once.** A budget opens on its budget page (`/b/{id}`, `?month=YYYY-MM`, the current month when absent), listed first in the sidebar; this ends ADR-071's "a budget opens on 所有帳戶". `GET /budgets/{id}/months/{month}` returns the pool, the month's income and, per expense category with money up to that month, the month's allocation and activity and the balance carried in (ADR-026); the client folds a pooled parent's subcategories into its envelope (ADR-061), so a parent whose children budget separately is a group line showing their sums and a subcategory inside a pooled parent shows only what was spent in it. `PUT /budgets/{id}/months/{month}/allocations` sets allocations of envelopes only (`not_an_envelope` otherwise), all or nothing, 0 removing one. - **ADR-079 Categories are edited on the budget page, which also lists income.** As in Actual Budget, the category tree is changed where the money is budgeted, and the separate category page (M3) is gone. The budget page lists two sections, 支出 (its heading carries the month's totals) and 收入 (each income category with what came in this month, from `incomes` in the month response; system categories such as opening balances only in a month they received something, and always last). Moving needs a new operation, `POST /categories/{id}/move` (`parentId`, `index` among the new siblings of the same kind): the new parent has the same kind, the tree stays three levels deep with the moved subtree (`category_too_deep`), a category cannot go under itself (`category_cycle`), and its entries and allocations stay on it, so moving into a pooled parent folds its money into that envelope. Category changes need `manage` (the owner); the page says so to other members. - **ADR-080 The budget page yanks, deletes, pastes and selects as the register does, by column.** The same keys work the same way wherever lines are edited: `yy`/`dd` (with counts), `p`/`P`, linewise `V` with `o`, `gv`, Esc and Shift-click, and `y`/`d`/`c` on the selection. Visual `>`/`<` move the selected siblings into the sibling above or out of their parent, and `:` from visual applies `:archive` and `:share` to the selection. This supersedes ADR-079's `dd` (only unused, never with subcategories). Whether a parent's subcategories share its budget is switched in place by a button on the parent's line (共用預算 / 各自預算), not only from the menu or `:share`. The page is at most 44rem wide, so a category's name stays close to its amounts.
- **ADR-081 The budget page shows one to three months, `y` keeps whole lines, and sharing is picked from a dropdown.** The viewer chooses 1, 2 or 3 months side by side (buttons in the header or `:months N`, kept in that browser's storage), starting at the month in the URL; fewer are shown when the window has no room (about 13.5rem a month). This supersedes ADR-080's in-place button and its column-only `y`.
- **ADR-082 A shared parent is only marked, not switched, on its line.** The dropdown of ADR-081 is gone: a parent whose subcategories share its budget shows a quiet 共用預算 beside its name, always and for every member, and a parent budgeting separately shows nothing (it reads as a group line with its subcategories' sums). - **ADR-083 One image: the API binary embeds the web app; deployed with Compose next to PostgreSQL.** The built SPA (`apps/web/dist/client`) is copied into `apps/api/internal/webui/static` and embedded with `go:embed`, so one binary serves the app and the API from one origin (no CORS, the session cookie and the cross-site guard of ADR-050 work unchanged). A plain `go build` embeds only a placeholder and serves just the API, so development keeps Vite on :3000; `mise run build` builds the full binary and removes the copy again. Every path outside `/api` is the app: files under `assets/` (content-hashed) are cached for a year, other files and the shell are revalidated, an unknown path without an extension gets the shell for the client router, and a missing file (with an extension) is a 404 so a stale asset after an upgrade never arrives as HTML; unknown `/api` paths keep the JSON error envelope. Every response carries `nosniff`, `X-Frame-Options: DENY` and `Referrer-Policy: same-origin`. The `Dockerfile` at the root builds the web app (Node, pnpm), then the binary (`CGO_ENABLED=0`, version from `-X main.version`), and runs it on `distroless/static` as nonroot; since that image has no shell, the binary answers `factual healthcheck` (GET `/api/healthz` on `FACTUAL_HTTP_ADDR`) for Docker's `HEALTHCHECK`. `deploy/docker-compose.yml` with `deploy/.env` runs it beside `postgres:18`, listening on 127.0.0.1 behind an HTTPS reverse proxy (the client IP for the login rate limit comes from `X-Forwarded-For`). Migrations stay applied on startup (ADR-007) and only go forward; backups are `pg_dump -Fc` of the database plus the `.env` (the encryption key). The image is built on the server from the repository for now; publishing it to a registry is left until someone else runs it. `docs/DEPLOYMENT.md` documents the variables, the proxy, backups, restores and upgrades.
- **ADR-084 Schedules are edited on a schedules page, as a grid, with the rule written in short Chinese**. Without slash blocks (ADR-077) schedules get their own page (`/b/{id}/schedules`, 排程, in the sidebar), a grid moved through and edited as the register is (pane `schedules`, `useKeyFeed`, counts, `o`/`dd`/`yy`/`p`/`u`, `V`, `:w` with drafts kept locally as ADR-043, its own `?` reference). A line is one schedule: 週期, 下次 (the next occurrence, which sets the start), 收款人 (or `@account` for a transfer), 備註, 分類, 帳戶, 支出/收入 (an amount starting with `~` is an estimate) and 預算方式 (ADR-086). The rule is typed as short zh-TW text, parsed in the browser (`apps/web/src/lib/schedule-rule.ts`, pure, tested with `pnpm test`) into an RRULE, and every rule is shown one way, however it was typed (`describeRule`: `每月 5 日`, `每 2 週一、五`, `每年 3/15，到 2030/3/15，遇假日延後`, which the parser reads back to the same rule), kept as `schedules.source`; the rules are `每天`, `每 N 天`, `每週一`, `每週一三五`, `每 2 週五`, `每月 5 日`, `每月最後一天`, `每月第 2 個週三`, `每 3 個月 5 日`, `每季 5 日`, `每年 3/15`, optionally followed by `到 2027/6/30`, `共 12 次`, `遇假日延後` or `遇假日提前`; the same rules may be written in English (`daily`, `every 2 weeks on fri`, `every weekday`, `monthly on the 5th`, `every month on the last day`, `monthly on the 2nd wed`, `quarterly on 10`, `yearly on mar 15`, then `until 2027/6/30`, `12 times`, `next workday`, `prev workday`), read whenever the text has Latin letters; typing `/` in the rule cell lists templates filled in for today (`/每月` or `/monthly` gives `每月 23 日`; `/every` filters them by their English names), and Enter opens the chosen one in the rule editor, a popover under the cell with one field per line (頻率, 間隔, the weekdays, the day or the nth weekday, the month, 結束, 遇假日; `apps/web/src/lib/rule-form.ts`, pure, tested), moved through with `j`/`k`; a choice changes with `h`/`l`, a number or the end date is text with a caret that `h`/`l` move, digits go in at the caret (the first one replaces the value) and `Ctrl-a`/`Ctrl-x` change the number under it (the year, month or day of a date), as Vim does; written back on Enter or Esc; `i` on a written rule opens it in the same editor, and `c` types it afresh; while a rule is typed the next occurrences are previewed, expanded in the same module (the subset of RRULE the parser writes: FREQ, INTERVAL, BYDAY with or without an ordinal, BYMONTHDAY including -1, BYMONTH, COUNT, UNTIL); the server expands with `rrule-go` and is what posts. `遇假日` moves an occurrence that falls on a day off to the next or previous working day by the holiday calendar of ADR-087. A schedule has one category or is one transfer; split schedules wait (loan payments of M11 are computed, ADR-032). `:schedule` on a register row creates a schedule like that transaction (rule `每月 <its day> 日`, `每月最後一天` after the 28th, which every month has), starting at the next occurrence after it and never before tomorrow: the transaction stays an ordinary one and nothing is posted at once; the schedule is adjusted on the schedules page. Schedules are written through `POST /budgets/{id}/schedules/batch` (all or nothing, errors per line, as ADR-044) and need `write`. M9 is done before M8, since M8's instalments are schedules; milestones keep their numbers. This supersedes ADR-033's DSL (schedules are not written as editor lines; `source` holds the rule text only).
- **ADR-085 A schedule turns into a transaction on its date; until then it shows as 預定**. A background job (on startup and hourly) creates every due occurrence (date up to today, in the server's time zone, `TZ`) that is not skipped, as a normal transaction with `schedule_id` and `occurrence_date` (unique, so reruns and missed days catch up without duplicates); an estimated amount makes it `needs_review`, and the register marks such rows (`?`, the amount with `~`) until they are edited (saving a transaction clears the flag) or confirmed with `:review` (`POST /budgets/{id}/transactions/reviewed`, the cursor's row or a selection). Occurrences of the next 30 days show in registers as dimmed 預定 rows after the real ones (`GET /budgets/{id}/schedules/upcoming`), above them in the newest-first register; they are not in the running balance, and a 預定 row's transaction id is derived from its schedule and occurrence, so a draft of an edited one finds it again. On a 預定 row, editing a cell and `:w` posts that occurrence with the change (it stays linked to its schedule), `:post` posts it now as it is, and `:skip` skips it (both also on a selection; `dd` on it is refused) (`schedule_skips`; `:unskip` on the schedules page brings it back). Editing a schedule changes every occurrence not yet posted; posted ones are ordinary transactions and are edited in the register. Paused schedules (`:pause`) post nothing and show no 預定 rows. A generated transaction belongs to whoever created the schedule. Saving a schedule that already has due occurrences (its next date is today or earlier) posts them in the same request, without waiting for the job. The job is a goroutine with a ticker, like the session cleanup: posting is idempotent through the unique key, so no job queue (River and the like) is needed; were several instances ever run, an advisory lock would keep them from posting at once.
- **ADR-086 Budget targets: a base amount per envelope plus the schedules it covers; `:fill` writes them**. As Actual's `#template schedule` (and its `full` option), each schedule chooses how it is budgeted (`schedules.budget_mode`): 不納入 (`none`), 到期月全額 (`full`: the sum of its occurrences in that month, so a weekly schedule counts four or five times) or 平均攤提 (`spread`: an occurrence's amount divided evenly over the months from the one after the previous occurrence (for the first one, from the month the schedule was made, but over no more months than the gap to the one after it) up to its own month; a month is the one the occurrence is posted in, after moving off days off, the remainder on the last, so a yearly 1,200 puts 100 into each month; for schedules monthly or more often it equals `full`). New schedules with an expense category start as `full`. Each expense envelope may have a base amount (`categories.budget_base`, set with `:base N` or the line's menu), never taken from last month's allocation, which already holds last month's schedules. An envelope's target for a month is its base plus what its covered schedules ask for that month (a schedule on a subcategory of a pooled parent counts for the parent's envelope, ADR-061; transfers, income and off-budget schedules count for nothing); the month response carries it with its parts, and the budget page marks an allocation that differs from its target and shows the parts in the status line. Nothing is allocated by itself: `:fill` sets the allocation of every envelope with a target in the cursor's month to that target (only the selected ones in visual mode), as one undo step through the allocations endpoint, and rerunning it changes nothing; allocations stay explicit, so editing a schedule never changes a past month or the pool. `:copylast` copies only envelopes without a target. Targets are computed on the server, which expands rules with `rrule-go`. Savings goals (M10) will add to the same target.
- **ADR-087 Days off come from the government's office calendar, imported by the admin**. Which days are off is the 行政院人事行政總處 calendar (中華民國政府行政機關辦公日曆表), which lists every day of a year with whether offices close, bridge days (補假, 調整放假) and make-up workdays (補班) included; Google's holiday calendar is not used, since it marks observances and make-up workdays alike and is not a published API. The days are kept for the whole instance in `holidays (date, is_off, note)`, not per budget. The instance admin imports a year on a settings page (國定假日), either from the URL of the official CSV (the server fetches it: http or https only, at most 1 MB, 10 s) or by choosing the CSV file; the format is the official one (`西元日期,星期,是否放假,備註`, UTF-8 with or without BOM, `2` off and `0` working), and an import replaces every year it contains, keeping its URL so it can be fetched again. Nothing is fetched by itself. A year without data counts Saturdays and Sundays as off. Posted transactions are never moved when a calendar arrives later; previews, 預定 rows and budget targets use the calendar as it is.
- **ADR-088 A card's statements follow its statement and due days, and close by themselves**. A credit card account keeps its 結帳日 and 繳款截止日 (`credit_cards.statement_day`, `due_day`), an optional credit limit and an optional autopay account, set when the card is created or later from its menu. Each card has one open statement (`statements.closed_at` null) whose period runs from the day after the last closing to the next statement day (the month's last day when it has no such day); its due date is the next due day after it (the same month when the due day is later than the statement day, else the next), moved to the next working day by the calendar of ADR-087. The day after the statement day the background job closes it: every card entry not yet billed and dated up to that day is billed in it (`entries.statement_id`), and the next statement opens; missed days catch up, one statement at a time. Entries keep the statement they were billed in when their transaction is edited; a transaction entered later with an earlier date is billed in the next statement, as a late posting is. In a card's register `:defer` takes rows out of the latest closed statement (the bank billed them a month later; the next closing bills them) or puts unbilled ones dated up to its closing day back (`PUT .../accounts/{id}/billing`); the status line says which statement the cursor's row is billed in, and the card's page lists its statements as the bank's bill does (previous amount, payments, spending, amount due). What a statement asks for (`amountDue`) is the card's outstanding balance over every billed entry at its closing (last time's unpaid rest included, never below zero); it is computed, unless the owner aligns it with the bank's bill (`statements.amount_due` set by hand, cleared to go back to the computed one). This refines ADR-029.
- **ADR-089 Payments count toward the latest statement by date**. A payment is a transfer into the card (an entry on the card without a category whose transaction moves money from another account). Whatever is paid after a statement closes counts toward it: its remainder is what it asks for less those payments, and its state is 待繳, 部分繳款, 已繳清 or 逾期 (past its due date with something left). An older statement is settled by the newer one, whose amount includes its unpaid rest, as the bank's bill does. Payments are not linked by hand: no payment dialog, and `entries.pays_statement_id` is left to autopay (ADR-090). This replaces ADR-029's linking of each payment to a statement.
- **ADR-090 Autopay is the card's own schedule, its amount taken when it posts**. A card with an autopay account gets a schedule (`schedules.card_id`) for the transfer from that account on the due day, moved to the next working day. It is not edited on the schedules page; its 預定 row shows in registers like any other, and at posting (or `:post`) its amount is what the latest statement still asks, so payments made before the due date lower it and nothing is posted when it is paid. Editing its 預定 row and `:w` posts the amount typed; `:skip` skips it. The posted transfer records the statement it pays (`entries.pays_statement_id`). An occurrence pays the latest closed statement when that is due within ten days of it, so it shows only once that statement has closed; one with nothing to pay is recorded as skipped. A due day after the 28th is the last of those days the month has (`BYSETPOS=-1`), as the statement's due date is.
- **ADR-091 Instalments: `:installment N` keeps the first and schedules the rest**. On a card purchase, `:installment N` makes the row one instalment (the total divided by N, the remainder on this one) and creates a monthly schedule on the row's day for the others, with the same payee, category and card, budgeted in full in their months (ADR-086), so the envelope is charged each period (ADR-030). Instalment dates already past when the command is given (an old purchase) count as paid and are not posted; the schedule holds only those still to come. A plan that started before Factual was used, a car loan before M11 among them, is a schedule written with what is left (`每月 5 日，共 7 次`) from the next payment; past payments are not entered.
- **ADR-092 An envelope can hold several goals, and its money goes to them in priority order**. This replaces ADR-031's one goal per category whose saved amount is the whole envelope balance; its four kinds stay. A goal has a name, a kind (目標金額 `target`, 期限前存到 `target_by_date`, 維持水位 `maintain`, 每月固定 `monthly`), its amounts, and optionally a note, a link and a 考慮到 date (`wait_until`); a thing the owner wants to buy is a goal with a link, not a separate list. It names an expense category and counts for the envelope that category is budgeted in (itself, or the pooled parent above it, as schedules do under ADR-061); a category in no envelope is refused (`not_an_envelope`). All goals of a budget form one ordered list (`goals.sort_order`), the priority. What a goal has saved is derived, never stored: its envelope's balance today (up to the current month, never below zero) is handed down the envelope's open goals in priority order, each with a total taking up to what it still needs (the target amount; for `maintain`, the level: `maintain_months` times the budget's average monthly spending over the last six complete months that have entries), and a `monthly` goal, which has no total, taking what is left. A goal is 存錢中 until it has saved its total, then 已存滿, or 冷靜中 while its `wait_until` is still ahead (a cooling-off period before buying); the owner marks it 已達成 (`achieved_at`) after buying the thing or deciding it is done, and from then on it takes nothing, so its purchase, recorded in the register as any spending, leaves the rest for the next goal; archived goals take nothing either. An envelope that pays bills and saves for a goal shares one balance between them; a goal on its own subcategory or envelope keeps them apart.
- **ADR-093 A goal's monthly amount joins its envelope's target, and `:fill` funds targets in priority order up to the pool**. Completing ADR-086 ("Savings goals will add to the same target"): an envelope's target for a month is its base, plus its schedules, plus what its open goals ask that month, each listed in the month response (`EnvelopeTarget.goals`) and named in the budget page's status line. A goal's ask is worked out from what it had saved at the start of the month (the waterfall of ADR-092 over the balance carried into it), so allocating the month does not change its target: `target` asks its monthly amount when it has one (at most what it still needs), nothing otherwise; `target_by_date` asks what it still needs divided by the months left up to and including the date's month, rounded up (everything from the date's month on); `maintain` asks the gap to its level, at most its monthly amount when it has one; `monthly` asks its monthly amount. A goal asks nothing in the months before the one it was made in, nor once achieved or archived. `:fill` now fills the cursor's month (or the selected envelopes) in order: every envelope's base and schedules first, in the page's order, then the goals in priority order, and stops where the pool would go below zero, listing what it could not fund in its message (what an envelope already has counts first, and one given more than its target gives the rest back); `:fill!` fills every target in full whatever the pool, as `:fill` did before. It is still one undo step, nothing is allocated by itself, and rerunning it changes nothing once the targets are met.
- **ADR-094 Goals are edited on a goals page, as a grid whose order is the priority, with progress and projected completion**. A goals page (`/b/{id}/goals`, 目標, in the sidebar after 排程) is a grid moved through and edited as the schedules page is (pane `goals`, `useKeyFeed`, counts, `o`/`dd`/`yy`/`p`/`u`, `V`, `:w` with drafts kept locally, its own `?` reference); its line order is the priority. As in Vim, `dd` takes a line out of its place: a saved goal goes to the bottom marked deleted until `:w` (`dd` on it again takes the mark off) and stays in the register, and `p`/`P` put that same goal back at the cursor, so `ddp` moves a goal one down and `ddkP` one up; a yanked line pastes as a new goal. The columns are 名稱, 類別, 類型, 目標 (the amount, or the months of a level), 期限, 每月, then 已存 (with a bar), 本月, 預計完成 and 狀態, which are worked out and never typed, then 考慮到, 連結 and 備註; `:done`/`:undone` mark a goal achieved, `:archive`/`:unarchive` archive it, `:wait N` sets 考慮到 N days ahead (30 by default, 0 clears it), and `gx` or `:open` open its link. The server lists the goals with what each has saved, still needs and asks this month (`GET /budgets/{id}/goals`) and saves the page's buffer in one transaction (`POST /budgets/{id}/goals/batch`, client ids as ADR-021, all or nothing with problems per goal as ADR-044); achieving and archiving are commands on the line. The response also carries what the projection needs: the budget's average monthly spending (for `maintain`), its typical monthly income (the median of the last six complete months that have entries) and the current month's targets without goals (bases and schedules), whose difference is 每月可自由分配, the money a month leaves for goals. - **ADR-095 Money in an envelope that is spoken for is shown apart, and moved between envelopes with `:move` and `:cover`**. What an envelope's schedules hold at the end of a month is what its targets asked for occurrences not posted by then: a full schedule's occurrence in its month or earlier, a spread one's shares of the months up to that one (ADR-086); skipped and paused ones hold nothing. Its goals share only the rest: the balance of ADR-092 (and the balance carried into a month for the asks of ADR-093) is now the envelope's balance less what its schedules hold, so a goal never counts money put by for a bill as saved. The month response lists both per envelope (`spokenFor`), and 可動用 is the balance less the two, below zero when the envelope holds less than they need; the budget page marks such a balance with a lock (red when 可動用 is below zero) and the status line spells it out. `:move N 分類` takes N from the envelope under the cursor and gives it to another in the cursor's month (two allocation changes, one undo step), and `:cover 分類` fills an overspent envelope's gap from another (`:cover` alone from the pool); both say when they dip into money spoken for, and neither refuses. An envelope is named by its path or a name only one envelope has.
- **ADR-096 A loan is set up from its terms, and its table is computed from them without any history**. A loan account (ADR-024, ADR-032) gets its terms in a 貸款設定 dialog, opened when a loan account is created or later from its menu, as a card's settings are (ADR-088): the amount lent (`loans.principal`), 撥款日 (`start_date`), 首期繳款日 (`first_payment_date`, whose day of the month is the payment day; after the 28th, the month's last of those days), the term in months, 本息平均攤還 (`annuity`) or 本金平均攤還 (`equal_principal`), the months of 寬限期 (interest only, `grace_months`), the rates (`loan_rates`: the first from 撥款日, later rows are rate changes from their date), the account it is paid from, the categories its principal and interest are spent in, and what an extra payment does (`prepay_mode`: 縮短期數 `shorten_term` keeps the payment and ends earlier, 降低月付 `reduce_payment` keeps the end and lowers the payment). Those terms alone determine every period: its date, principal, interest and the principal left after it, so a loan taken years before Factual was used needs no past payments entered. The rules, computed on the server only (`internal/domain/ledger/loans.go`, tested against bank-style tables) and repeated nowhere else: a period's interest is the principal left at its start times the annual rate divided by twelve, at the rate in effect on the day after the previous payment date (on 撥款日 for the first period), rounded half up to the minor unit; the first period's interest is counted by days (days ÷ 365) when the first payment date is not one month after 撥款日; grace periods pay only interest; an annuity's payment is the level payment over the months left (recomputed at each rate change and, for `reduce_payment`, after an extra payment), an equal-principal loan repays the principal left divided by the months left; the last period takes whatever principal remains, so the loan ends at exactly zero. Small differences from a bank's own rounding or day count are expected and are corrected by aligning (ADR-098), not by modelling each bank. The dialog previews the monthly payment and the table while terms are typed (`POST .../accounts/{id}/loan/preview`, `read`, nothing stored) so the owner can compare them with the bank's figures before saving; the terms are saved with `PUT .../accounts/{id}/loan` (`write`) and removed with `DELETE` (which also removes its schedule and keeps posted transactions). Storing the table was rejected (ADR-032: rate changes and extra payments would have to rewrite it); so was requiring past payments, and generating them, which would rewrite the paying account's history and the pool. Setting terms changes no money by itself: what the loan account owes is set apart from them (ADR-098).
- **ADR-097 Payments are the loan's own schedule, split into principal and interest when they post**. Saving terms creates one schedule for the loan (`schedules.kind = 'loan'`, `loan_account_id`, no `schedule_entries`), monthly on the payment day from the first payment not yet due, moved off days off as the owner chooses (遇假日延後 by default, as banks debit; the period's interest is still counted to its nominal date); like autopay (ADR-090) it is not edited on the schedules page, whose batch refuses it, and is changed through the terms. Its amount is computed when it posts or is listed, from the table recomputed on the loan account's actual balance at the start of the period, so an extra payment lowers every later period's interest, and with `reduce_payment` the payment too. A posted payment is one transaction: the paying account gives the principal in the principal category and the interest in the interest category (two categorized entries, so the money leaves the budget from those envelopes), and the loan account receives the principal (no category, off budget); a grace period posts only the interest. Its 預定 row shows in registers like any other schedule's, as a split of those lines; editing it and `:w` posts the amounts typed (the bank's own figures for that month), `:skip` skips it (posting nothing; the next period is computed on the balance as it is), and `:post` posts it now. An extra payment is an ordinary transfer into the loan account entered in the register, with the principal category (ADR-032); anything entered on the loan account between two payments (an extra payment, an alignment) lowers what is owed from the period after the next payment on, since a period's interest is counted on what was owed at its start. A posted payment's figures are its transaction's (the loan account's entry is the principal, the rest it paid is interest), so editing a posted payment in the register is how the bank's figures are kept. The schedule's budget mode is 到期月全額 by default (ADR-086): each month's target gets the projected principal in the principal category's envelope and the projected interest in the interest category's (listed as the schedule's shares with the loan's account, `ScheduleShare.loanAccountId`, since the schedule is not on the schedules page and the budget page names it after the loan), `setAside` holds them until they post (ADR-095), and `:fill` funds them with the other schedules. When the last period posts, the schedule ends and the account can be closed. A plan already written as an instalment schedule (ADR-091) is replaced by deleting that schedule and setting up the loan.
- **ADR-098 What a loan owes is aligned with the bank, and the loan's page shows its table**. Saving terms computes the principal left today (after the last period due), and the dialog compares it with the loan account's balance: an account with no entries gets an opening balance of minus that amount on the date of the last period due (the payments before it are not entered); one that already has entries (payments recorded by hand, perhaps with their interest counted as principal) shows the difference, and 對齊 posts an adjustment of it on the loan account alone (a transaction with one off-budget entry and no category, payee 貸款調整, which changes neither the pool nor an envelope). The same 對齊 is available any time from the loan's menu with a date and the principal the bank shows that day (`POST .../accounts/{id}/loan/align`, `write`), which is how a missed rate change, a past extra payment, or a bank's different rounding is fixed: later periods are computed from the aligned balance. A rate change is a new row in 利率 (date and rate) in the same dialog; periods not yet posted change, posted ones never do. The loan account's page shows, above the register as a card's statements do: the principal left, principal repaid and interest paid to date, the periods left, the next payment, and the payoff date; and the table (`GET .../accounts/{id}/loan`), with past periods taken from the terms, posted ones marked with their actual figures, and later ones projected. Interest paid to date is the computed interest of the periods before the loan was set up plus the interest of the payments its schedule posted (the interest entries of transactions with its `schedule_id`); principal repaid is the amount lent less what is left. A loan with no terms keeps working as before: an off-budget account whose balance moves only by the transactions entered.
- **ADR-099 Registers keep loading whole; API responses are gzipped, month figures are loaded once per request, and row statuses are kept per row**. Measured with seeded ledgers of 5k, 20k and 50k transactions over five years: one busy account's register stays under half a second at 50k (server and browser together), a multi-account view passes a second only near 50k, and a typical household's five years (about 5k) is under 0.1 s everywhere. Paging or loading a date window (with the balance before it from the server, so running balances still hold) is therefore left until a ledger nears 20k transactions; it will need an index on `(budget_id, date, created_at, id)` and a way for drafts and undo to refer to transactions not loaded. What showed first was fixed instead. API responses were sent uncompressed (gzip wrapped only the web app), about 420 bytes a transaction, so a 20k-transaction view was 8 MB over the network: every API route is now gzipped at the fastest level above 1 KB (about five times smaller; 20 MB in about 90 ms). The month response ran the whole-ledger aggregations several times (the envelopes' month three times and the six-month totals twice, through targets, goal asks and what is spoken for), as did the goals list: a request now loads them through one `budgetFacts` (`internal/domain/ledger/facts.go`), each at most once per month asked for. The register compared every row with its saved transaction on each edit, twice (once for drafts), which cost 100–250 ms an edit in large views: `rowStatus` now remembers its answer per row and context, which is safe because rows are never changed in place, so an edit compares only the rows it made (about 20 ms at 50k, most of it the running balances).

References are real file references (`./accounts.yaml#/schemas/Account`, `#/schemas/LoanRate` inside a file), so editors resolve them. `mise run gen` first runs `redocly bundle` (`@redocly/cli`, a root devDependency pinned exactly, telemetry off), which hoists every referenced parameter, response and schema into `components` under its own name, and writes the result to `apps/api/api/openapi.yaml`; oapi-codegen, the embedded spec the server validates against and checks `x-auth`/`x-budget` on (ADR-057), and openapi-typescript all keep reading that one generated file. Schema names must therefore stay unique across files (a clash would be renamed by the bundler, changing the generated types), and a schema reaches the bundle only when something references it: one needed while unreferenced is listed under `components.schemas` in `root.yaml`, which takes over from `skip-prune` (ADR-004) for that case. Splitting was checked by bundling: the result equals the old file apart from the order of its components, and the generated Go code is unchanged apart from its embedded spec. Leaving oapi-codegen to follow cross-file references was rejected (it treats another file as another Go package, and the embedded spec could not resolve them at run time), as was a custom merge of fragments (editors could not resolve `#/components/...` inside a fragment) and one file per schema (over a hundred files).
- **ADR-114 The API serves its own reference at /api/docs, when enabled.** Like FastAPI's `/docs`, the Go server serves a Scalar page at `/api/docs` that reads `/api/openapi.json`, the spec the server validates against (ADR-113), so the reference always describes the running server without another process or build step, and its test requests go to the same origin with the caller's session cookie (no CORS, and the cross-site guard lets them through). It is registered next to `/api/openapi.json`, outside the session and access checks, and only when `FACTUAL_API_DOCS` is true: on in local development (`apps/api/mise.toml`), off by default in production, where the spec stays public at `/api/openapi.json` for integrations. Scalar is loaded from jsDelivr at a pinned version with a subresource-integrity hash, so the binary does not grow by its ~5 MB bundle; its telemetry, web fonts, request proxy (`proxy.scalar.com`), AI agent and MCP generator are turned off, so the page talks only to the CDN and the server. A separate docs server in the dev stack (Redoc or Scalar served from `spec/`) was rejected as one more process that the API itself can replace.
- **ADR-115 Groups reuse the friend's splitting among any of their members; balances and who-pays-whom are worked out, never stored**. A group (M13, ADR-037) is created by a user, its admin, with some of their friends: placeholders, or new names, which become placeholder friends (a friendship without a friend account until a direct expense needs one, `ensureFriendAccount`); friends with an account join with M15, when other people's budgets are written to (`registered_member`). Its currency is the creator's default budget's (ADR-041), and it has one account in that budget (`accounts.group_id`, `kind = 'friend'`, on budget, never written by hand like a friend account), whose balance is the user's net position in the group. Its expenses are saved exactly as a friend's (ADR-106): the same batch (`saveExpenses` with an `expensePlace`), the same plan (`planExpense` over a `splitScope` of members; with a friend the scope is the two, both always sharing, and a settlement's receiver may be left implicit), the same transaction written for the caller on the group account; any member may pay (several each once), the split is among any of them (equal among those listed, exact, percent or shares, divided in the order sent, member order from the browser), a settlement is from one member to another named one, and an expense that does not involve the caller writes nothing for them. Each member's balance (what they paid less their shares) is summed from the group's live expenses when the group is read (`ListGroupMembers`), and the browser works out the same from its lines, saved or not (`memberBalances`), with the suggestion of who pays whom (`settleUp`: the largest debt to the largest credit until nothing is owed, ties to the earlier member), which `:settle` adds as settlement lines; the ledger keeps only net positions, so the suggestion never touches it. Only the admin renames a group, changes its members (a member named by a live expense stays, `member_in_use`) or archives it, which needs every balance at zero (`group_not_settled`), closes the group account and refuses expenses (`group_archived`) until it is unarchived; a group without expenses can be deleted with its account (`group_in_use` otherwise), and a friend still in a group is not removed (`friend_in_group`). The friend's page and the group's page are the same grid (`expense-grid.tsx`, `SplitScope`), over a split model generalized to members (`apps/web/src/lib/split.ts`: payers, receiver, `among`, `amounts`, `weights` by member id; drafts moved to version 2); with a friend it keeps M12's cells and form, where the friend's part is what the caller's leaves, and in a group the split form lists the members (分/不分, each one's amount, percentage or shares). Shared expenses are now stamped with the clock (`created_at = clock_timestamp()`) so the lines of one batch keep their order.
- **ADR-116 Lists are grids saved with :w; the 分帳 page is one**. Every page where the user adds, changes or removes things in a list is a Vim-style grid like the register's (ADR-045, ADR-108): normal, visual and insert modes through `useKeyFeed`, `o`/`dd`/`u`, `gx` to open a line's own page, changes kept in the page's buffer and its draft (ADR-043) and saved with `:w` through one batch endpoint, all or nothing with problems per line (ADR-044); values with parts are forms under the cell (ADR-107), larger settings lines under their line (ADR-110), yes/no a ticked column (ADR-111). Dialogs remain only for confirming something irreversible and for pages that are not lists. This was already how the register, budget, schedules, goals, accounts and friend pages worked; it is now the default for new pages, and the 分帳 page follows it: groups first, then friends, each a line (名稱, 類型 chosen from the completion list on a new line, 成員 edited in a form listing the friend lines including unsaved ones, 筆數 and 往來 derived, 封存 ticked with `x`), saved through `POST /splitting/batch` (`SaveSplitting`: new placeholder friends keyed by the client's ids with their friend accounts, renames, groups created or changed with their members replaced and archiving, then deleted groups and deleted friends, each checked as the single-item endpoints check it). It replaces the add, rename and remove dialogs of the friends list (M12) and the group dialog of ADR-115, whose members could be typed as new names; a new person is now a friend line, ticked into the group in the same buffer. The single-item endpoints stay for the API. Balances that are zero read 已結清 rather than 兩清.
