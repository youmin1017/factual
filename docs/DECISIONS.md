# Decisions

Format: ADR-NNN — decision, reason. Add a new entry (do not rewrite history) when architecture changes; an entry that replaces an older one says which. Entries marked *(planned)* are decided but not implemented yet.

## Platform and tooling

- **ADR-001 Monorepo, `apps/api` + `apps/web`.** One repo, pnpm workspace for the web app, independent Go module (`factual/apps/api`) for the API.
- **ADR-002 Self-hosted, server-authoritative.** One Go API and one PostgreSQL database are the single source of truth. No local-first/CRDT sync as in Actual Budget: expense splitting writes into several users' ledgers at once, which needs one consistent store. Offline use is out of scope.
- **ADR-003 PostgreSQL 15+.** The schema relies on deferred constraint triggers, `unique nulls not distinct` and `on delete set null (column)`. Local development and integration tests run PostgreSQL 18 from `docker-compose.yml`.
- **ADR-004 echo v4, spec-first OpenAPI with oapi-codegen (strict server).** `apps/api/api/openapi.yaml` is the source of truth; handlers implement the generated interface; requests are validated by echo-middleware. `skip-prune` keeps shared schemas (the `Error` envelope) that no operation references yet.
- **ADR-005 Web API types are generated from the same spec.** openapi-typescript writes `apps/web/src/lib/api.gen.ts`; calls go through openapi-fetch and its TanStack Query bindings (`api` / `$api` in `src/lib/api.ts`). No hand-written response types.
- **ADR-006 sqlc on pgx/v5, one private package per domain.** A domain's SQL in `internal/domain/<name>/queries/*.sql` is generated into `internal/domain/<name>/internal/db`, which no other package can import. `uuid` maps to `google/uuid`, `timestamptz` to `time.Time`.
- **ADR-007 goose SQL migrations, embedded and applied on startup.** Migrations in `apps/api/db/migrations` are compiled into the binary and run when the API starts (`FACTUAL_DB_AUTO_MIGRATE`, default on), so a self-hosted install needs no separate migration tool. sqlc reads the same directory as its schema. Atlas (used in the go-admin template) was rejected: the schema needs triggers and functions, which Atlas only diffs in its paid edition.
- **ADR-008 Configuration is environment variables only (`FACTUAL_*`).** Few settings, and env vars are what self-hosted deployments (containers, systemd) use. Local development values live in `apps/api/mise.toml`; personal overrides in a git-ignored `mise.local.toml`. No config files, no koanf.
- **ADR-009 mise for tools and tasks, dekit for the dev stack, lefthook for hooks.** mise pins every tool version and holds all tasks (monorepo mode: `//apps/api:<task>`, `//apps/web:<task>`). `mise run dev` opens dekit (`dekit.yaml`: db, API with air, web). Git hooks are the tracked `.githooks/pre-commit`, which runs lefthook; `mise run setup` enables it through `core.hooksPath`.
- **ADR-010 TanStack Start (React) in SPA mode.** Chosen over Nuxt. Both were viable and the performance difference is not noticeable for this app (a virtualized grid renders a few hundred cells); the reasons are typed, validated URL search params for ledger state (month, account, filters) and first-class React support in TanStack Table/Virtual/Query. The React Compiler is enabled. The app sits behind a login and all data comes from the Go API, so the build is a static SPA (`dist/client`, entry `_shell.html`); server functions and SSR are not used.
- **ADR-011 oxlint and oxfmt, extending the TanStack shared configs.** `@tanstack/oxlint-config` (type-aware, needs `oxlint-tsgolint`) and `@tanstack/oxfmt-config` replace the ESLint + Prettier toolchain the scaffold came with. The shared lint config is framework-agnostic, so `oxlint.config.ts` adds the React plugin (hooks rules, `jsx-key`). Formatting follows the TanStack config, not the go-admin template's.
- **ADR-012 Go is linted and formatted with golangci-lint** (standard linters, goimports), generated code excluded.
- **ADR-013 UI text is Traditional Chinese (zh-TW)**, written directly in components. Code, identifiers and API error codes are English.

## Users and access

- **ADR-014 Built-in accounts with server-side sessions.** Username + password (argon2id), sessions stored in PostgreSQL and referenced by an HttpOnly cookie; only the hash of the session token is stored. OIDC login may be added later as an option.
- **ADR-015 Invite-only registration; the first user is the instance admin.** *(planned)* Fits a self-hosted instance shared with friends. Everyone a user can split with is an account on the same instance; there is no federation.
- **ADR-016 Placeholder members are `users` rows without a password.** A friend who has not registered yet can already take part in shared expenses. They register through an invite that claims that row (`invites.claims_user_id`), so nothing has to be merged afterwards.
- **ADR-017 Authorization is plain Go, no casbin.** Roles are few and fixed (budget: owner/editor/viewer; group: admin/member), so a typed role -> permission map behind one `Can()` function and one middleware is enough and is checked by the compiler. What is actually hard here (list filtering, visibility of shared expenses, "only the recorder may edit", privacy between participants) is data relationships, solved by SQL scoping and table structure, which a policy engine does not help with. Revisit if permissions must become configurable at runtime.
- **ADR-018 A budget can have several members, but v1 ships personal budgets plus splitting.** `budget_members` with roles exists so shared budgets (e.g. a couple) need no schema change later. Splitting happens between users, not budgets: each user names a default budget (`users.default_budget_id`) that receives their side of a shared expense.
- **ADR-019 Tenant isolation is enforced in the database.** Every table inside a budget carries `budget_id` and references its parents with composite foreign keys `(budget_id, id)`, so a row can never point at another budget's account, category, payee or transaction.

## Ledger and budgeting

- **ADR-020 Money is `bigint` minor units.** No floating point. An entry's amount is the change in its account's balance: positive increases it, negative decreases it. Liability accounts (credit cards, loans, money owed to friends) have negative balances.
- **ADR-021 Primary keys are UUIDs the client may generate.** `:w` commits a batch in which new rows reference each other (a transfer's two sides, a split and its transaction) and may be retried; client-side ids (UUIDv7 recommended) make that possible without a round trip.
- **ADR-022 A transaction is a header plus entries `(account, category?, amount)`.** One row in the editor is the entries of one transaction on the account being viewed. A plain expense is one entry; a split is several entries on the same account; a transfer is two entries without a category.
- **ADR-023 The ledger invariant follows cash, not net worth.** Per transaction, entries without a category on on-budget accounts must sum to zero, and entries on off-budget accounts never carry a category. A deferred constraint trigger checks this at commit. It guarantees *on-budget account total = pool + all envelope balances*. Pure zero-sum double entry was considered and rejected: paying loan principal is not an expense there, but the cash is gone, so envelopes would stop matching the money available. Moving money to an off-budget account therefore always needs a category.
- **ADR-024 Accounts are on-budget or off-budget.** Cash, bank, credit card, friend/group and suspense accounts are on-budget; loans and investments are off-budget (tracked for net worth only). The flag cannot change once an account has entries.
- **ADR-025 Income goes to a pool, not to a month.** Entries with an income category feed a timeless pool; the user decides how much to move into each envelope per month (`allocations`, one row per category and month). Unlike Actual Budget, income does not become "to budget" for the month it arrives in, so irregular income does not inflate a month, and the pool shows the remaining runway.
- **ADR-026 Envelope balances are cumulative sums; there is no month close.** Balance = allocations to date + activity to date, carried forward whether positive or negative. Nothing is stored per month besides the allocation itself. A cache table may be added if sums become slow.
- **ADR-027 Categories form a tree of at most three levels.** Budgets sit on leaves by default and parents show totals; a parent with `pooled = true` owns one envelope shared by its children. Names are unique within a parent and cannot contain `/`, which is the path separator in the editor (`交通/加油`).
- **ADR-028 Credit cards are on-budget accounts with a negative balance.** Spending on a card lowers the envelope and raises the debt in the same entry, so the money to pay the card is always set aside. The "reserve" shown for a card is derived from its balance, never stored, so it cannot drift.
- **ADR-029 Credit card statements are first-class.** A statement has a period, due date and amount due; entries record which statement bills them and which statement a payment settles. Paying a card is a transfer linked to a statement, which lets the app show what is due, what is covered and what is missing.
- **ADR-030 Instalments are schedules in v1.** A purchase paid in N instalments is a schedule with N occurrences, so the envelope is charged each period. Charging the envelope once while billing over several statements needs one entry spread across statements and is deferred.
- **ADR-031 A savings goal attaches to a category.** The amount saved is that category's envelope balance; progress and estimated completion are derived. Kinds: target amount, target amount by a date, maintain a level (N months of average spending, for an emergency fund), fixed monthly amount.
- **ADR-032 Loans are off-budget accounts; the amortization schedule is computed, not stored.** A loan keeps principal, term, method (annuity or equal principal), grace period and its rate periods (`loan_rates`, the first row being the initial rate). Each payment is generated by a schedule and split into a principal entry (a categorized outflow plus the matching reduction of the loan account) and an interest entry. Extra principal payments are ordinary entries; the schedule is recomputed from them.
- **ADR-033 Schedules generate transactions directly; nothing is matched.** A schedule is a transaction template plus a recurrence rule. Each generated transaction is unique by `(schedule_id, occurrence_date)`, so reruns never duplicate and no heuristic has to guess which transaction belongs to which occurrence (the opposite of Actual Budget's matching). The rule is stored as an iCalendar RRULE compiled from the editor's DSL, alongside the line the user wrote (`source`) so the editor can show it back. An estimated amount (`~`) produces a transaction marked `needs_review`.

## Splitting

- **ADR-034 A shared expense lives outside any budget.** `shared_expenses` with its payers and shares belongs to the users involved (optionally a group). The database checks at commit that payments and shares each sum to the total. A settlement is a shared expense of kind `settlement`: the payer pays, the receiver's share is the whole amount.
- **ADR-035 Each participant gets exactly one transaction in their own budget.** It is generated from the shared expense and linked to it (`unique (budget_id, shared_expense_id)`). When the recorder edits the expense, amounts are regenerated but the participant's own category and note are kept. Transactions created for someone else arrive marked `needs_review`.
- **ADR-036 Money between people is an on-budget account per friend or per group.** Every participant records their share as a categorized entry on that account; a payer additionally transfers what they paid into it. The balance is then what the user is owed (positive) or owes (negative). Owing a friend works exactly like a credit card: the envelope is charged when the expense happens and repaying is a plain transfer. Money advanced for others is not the payer's expense.
- **ADR-037 A group has one account per member, not one per pair.** The balance is the member's net position in the group, so debt simplification only changes the suggestion of who pays whom and never touches the ledger. Direct splitting between two friends uses one account per friend.
- **ADR-038 A payer who did not record the expense pays from a suspense account.** The recorder cannot know which of the other payer's accounts was used, so that side is posted to the budget's suspense account and marked `needs_review` until its owner picks the real account.
- **ADR-039 Categories are inherited through a hint, then mapped.** The shared expense carries the recorder's category path as text. Each participant's category is chosen in this order: the default category of that friend/group account, the participant's own mapping from that hint (remembered once corrected), a category with the same path, otherwise an inbox category. Changing the category affects only the participant's own budget.
- **ADR-040 Participants see the shared expense, never each other's ledger.** Shared expenses and budget transactions are separate tables and the splitting API only returns the former. The category hint is the one deliberate exception.
- **ADR-041 Budgets have one currency; shared expenses may record a foreign one.** A shared expense is settled in the group's currency and can keep the original currency, amount and the exchange rate at the time. v1 assumes the group's currency equals its members' budget currencies.

## Editor

- **ADR-042 Vim-style editing in two parts.** *(planned)* The transaction grid implements normal-mode navigation and row operations itself (a small state machine); the slash-command draft blocks (`/add`, `/schedule`, ...) are CodeMirror 6 with its Vim extension, with completion sources for payees, categories, accounts, friends and groups.
- **ADR-043 Drafts are saved locally; only `:w` commits.** Unsaved changes survive a crash but nothing reaches the server until the user writes, because a commit can notify other people (splits).
- **ADR-044 `:w` is one atomic batch.** A single endpoint takes every create, update and delete of the buffer, applies them in one database transaction and returns errors per row for the editor to mark. The DSL is parsed in the browser (it is needed there for completion and live validation); the server accepts structured JSON only and validates it again.
- **ADR-045 Grid performance rules.** The grid is virtualized; the cursor is a single overlay element rather than per-cell state; a cell being edited keeps its text locally and writes back on leave; one key listener sits on the grid. These matter more than the choice of framework (ADR-010).

## Login

- **ADR-046 OpenID Connect login, with providers configured in the web app.** The instance admin adds identity providers by issuer URL on a settings page; anything that serves OIDC discovery works, and no config file or restart is involved. The flow is the authorization code flow with PKCE, state and nonce; its state travels in a short-lived encrypted cookie, not in the database. Same design as the go-admin template.
- **ADR-047 An identity logs in only after its owner linked it.** A user logs in with a password, links an identity from their profile, and can use it from then on. Identities are matched by (provider, subject), never by email, and an unknown identity is rejected rather than turned into a new user: an identity provider must not be able to create accounts or take one over through a matching email address. Registering through an invite with an identity instead of a password belongs to the invite feature (ADR-015).
- **ADR-048 Client secrets are encrypted at rest; the key comes from the environment.** `FACTUAL_ENCRYPTION_KEY` (AES-256-GCM) seals identity providers' client secrets and the flow cookie. The API never returns a secret; an empty secret on update keeps the stored one. Without the key OIDC login is unavailable and the settings page says so. Keeping the key in the database was rejected: it would sit next to the secrets it protects.
- **ADR-049 The first admin is created from the environment.** While nobody can log in, startup creates the user in `FACTUAL_BOOTSTRAP_ADMIN_USERNAME`/`_PASSWORD` as instance admin and refuses to start without them. This is the "first user is the instance admin" of ADR-015; a first-run setup page was rejected because whoever reaches a fresh instance first would become its admin.
- **ADR-050 Session cookie and CSRF.** The session token is random, httpOnly, SameSite=Lax and Secure whenever `FACTUAL_PUBLIC_URL` is https; only its SHA-256 is stored. State-changing requests that the browser marks as cross-site (Fetch Metadata) are rejected, which together with SameSite=Lax is the CSRF protection, so no token has to be threaded through the web app. Sessions end after 30 days idle or 90 days in total by default, and all other sessions end when the password changes.
- **ADR-051 Every operation declares `x-auth` in the spec.** `public`, `authenticated` or `admin`; a missing declaration stops the API at startup, so an endpoint cannot be exposed by forgetting a check. This is the instance-level part of ADR-017; budget and group roles will be checked in the domains.
- **ADR-052 shadcn/ui for web components.** Radix primitives with Tailwind, copied into `src/components/ui`. The app is keyboard-driven and will need unusual focus and key handling (the Vim grid, completion menus); owning the component source makes that possible without fighting a library, while forms, dialogs and menus still come ready-made and accessible. Vendored components are excluded from oxlint.

## Visual design

- **ADR-053 A ledger in blue-black ink, dark by default.** The theme is a bookkeeping ledger: blue-black ink and ledger paper as the two grounds (dark and light mode), kraft envelope as the one accent for primary actions, the cursor and focus, the ledger's blue ruling for borders, red for negatives (赤字) and jade for positives. Dark is the default; light is the same ledger on paper; the choice is per browser (next-themes, `localStorage`). Colours are the shadcn CSS variables in `apps/web/src/styles.css` plus `--positive`, `--rule` and `--kraft`; components use the tokens, never raw colours.
- **ADR-054 One typeface with a mono axis.** Recursive (variable, self-hosted via Fontsource) is proportional for the interface and monospaced (`MONO` axis) for figures, identifiers and the editor, so the Vim grid and the rest of the app share letterforms. Chinese falls back to the system's Traditional Chinese face. Amounts use `.amount` (tabular figures; `.amount-negative`, `.amount-positive`).
- **ADR-055 The app is framed like an editor.** A sidebar of places, the page, and a status line along the bottom (section and page, connection, user), which is where editing mode and unsaved changes will show once the grid exists. The block cursor after the wordmark is the product's mark; it blinks only on the login page, where the app waits for input.

## Budget setup

- **ADR-056 TWD is kept in whole 元.** Amounts are integers in a per-currency minor unit (ADR-020); the API returns it with each budget as `minorUnits`. Currencies whose smaller units are not used in practice (TWD, JPY, KRW and a few others) have 0, the rest 2. A budget's currency cannot change after it is created.
- **ADR-057 `x-budget` declares the permission an operation inside a budget needs.** `read`, `write` or `manage`, checked by one middleware against the caller's role (ADR-017) before the handler runs; a path with `{budgetId}` that does not declare it stops the API at startup. A budget the caller is not a member of answers 404, like one that does not exist. Handlers then trust the budget id and scope every query by it. Viewers read, editors also write transactions and allocations, owners also change accounts, categories and members.
- **ADR-058 A user creates their first budget explicitly.** Logging in without a budget opens a setup page (name, currency, a starter set of categories) instead of creating one silently, so the currency is chosen once and on purpose. The first budget a user creates becomes their default (ADR-018).
- **ADR-059 Opening balances are transactions marked `is_opening`.** On an on-budget account the opening balance is recorded in the system income category `opening_balance` (identified by `system_key`, not by name), so it reaches the pool like other money coming in; on a tracking account it has no category. An account whose only transaction is its opening balance can still be deleted, and its opening balance goes with it; once it has other transactions it can only be closed, and only with a zero balance.
- **ADR-060 Categories are archived rather than deleted once used.** Deleting a category is refused while it has subcategories, entries, allocations, schedules or a goal, because allocations and goals would otherwise be deleted with it. Archived categories, and everything under them, are hidden from the category page until asked for.
- **ADR-061 Subcategories share their parent's budget by default.** New expense categories, the starter set included, are created with `pooled = true`, so a budget is set on the top-level category and its subcategories draw from it; turning it off on a parent budgets each subcategory separately. This replaces "budgets sit on leaves by default" in ADR-027. Income categories never pool.
- **ADR-062 The UI says 預算, not 信封.** What the code and these ADRs call an envelope (a category's allocated money and its balance) is shown to users as that category's 預算 (e.g. 共用預算, 還沒分配到預算的錢). The word 信封 does not appear in the interface; the README still names the method 信封式預算.

## Account register

- **ADR-063 A register row is one transaction seen from one account.** Columns follow the order the user writes a line: date, payee, note, category, outflow, inflow, cleared, with the running balance last. Money is entered in separate outflow and inflow columns, as amounts typed without a sign. A row with several entries on the account, or entries on more than two accounts, is a split: its date, payee, note and cleared state are edited in the grid, its category and amount in the split editor (still to come).
- **ADR-064 Transfers are written as `@account` in the payee cell.** The row then stands for two entries, one per account. Its category cell is used only when the transfer crosses between a budget and a tracking account (ADR-023), and then belongs to the budget side, so loan principal is recorded from either account's register. Within the budget, or between tracking accounts, a transfer has no category. Cleared is per entry: clearing a transfer in one register leaves the other side as it was.
- **ADR-065 The batch endpoint replaces whole transactions and reports problems per transaction.** `POST /budgets/{id}/transactions/batch` takes upserts keyed by the client's ids and a list of deletes, validates every transaction against the ledger rules before writing, and answers 422 with problems by transaction id and field when any fail, saving nothing. Payees are sent by name and created on first use; the payees list carries each payee's last category so the editor can fill it in.
- **ADR-066 Running balances follow time, not the screen.** The register shows the newest transactions first and computes balances on the client: by date, then within a day the opening balance, saved rows and unsaved rows, each from the bottom of the screen up. Where `o` puts a new row does not change the balances above it.
- **ADR-067 The editor keeps Vim's names and keys.** Normal mode moves with `hjkl`, `w`/`b`, `gg`/`G`, counts and `Ctrl-d`/`Ctrl-u`; `i`/`a`/`Enter` edit a cell, `c`/`s` replace it; `o`/`O`, `dd`, `yy`/`p`/`P`, `x` (cleared), `u`/`Ctrl-r` and `.` work on rows; `:w`, `:q`, `:q!`, `:wq`, `:e!` and `:<n>` are commands. Insert mode completes payees, `@` accounts and category paths, and Tab walks the editable cells of the row. The status line names the mode as Vim does (NORMAL, INSERT, COMMAND) and counts unsaved rows. Dates accept `t`, `y`, `-1`, `5`, `11/5` and full dates; amounts accept arithmetic.
- **ADR-068 Splits are lines, edited in a window under the register.** A transaction seen from one account is a list of lines: each entry on the account is a line, and each entry on another account pairs with a line of the opposite amount, which becomes a transfer line (a loan payment from the bank is a principal line transferred to the loan plus an interest line). A row with one line is an ordinary row (a category, or `@account`); with several it is a split, and its category and amount cells open the split editor, a window under the register like Vim's `:split` with columns transfer account, category, memo, outflow, inflow. It opens from a split's cells, the category completion "拆分成多個類別…" or `:sp`; `o` adds a line carrying what is left of the amount the row had when the window opened; `q` closes it and applies the lines as one change (`u` undoes it). Empty lines are dropped and a single remaining line turns the row back into an ordinary one. Entries that do not pair up from this account's side (a split written from another account) are shown as a locked row that names the account to edit it in. Drafts moved to version 2; older drafts are dropped.
- **ADR-069 Payees are renamed, merged and deleted on their own page.** Renaming onto another payee's name is refused (`payee_exists`), so that two payees never silently become one; merging moves the transactions and schedules of the sources to the kept payee and deletes the sources in one database transaction. Only a payee nothing uses can be deleted. Editors and owners may do all three (`x-budget: write`); the list carries each payee's transaction count.
- **ADR-070 Key mappings are a vimrc kept on the server.** Each user has one text of mappings (`users.editor_keymap`, `GET/PUT /me/preferences`) so they follow the user to every device. The web app parses it (`apps/web/src/lib/keymap.ts`): `nnoremap`/`nmap`/`noremap`/`map` for normal mode, `inoremap`/`imap` for insert mode, `let mapleader` and `<Leader>`, Vim's key notation; lines it does not understand are skipped and shown on the editor settings page (設定 → 編輯器), which will also hold the editors' other options. Every mapping is non-recursive. Normal mode waits up to a second for a longer mapping as Vim's `timeoutlen` does. Insert mode lets characters type and takes them back when the last ones complete a mapping (`jk` → `<Esc>`), and leaves keys composing Chinese input alone. Keys a mapping produces run one per render, so `:w<CR>` opens the command line, types and runs like typed keys. Command-line mappings are not supported. The CodeMirror 6 slash blocks (M5) use the same parsed mappings: each one is handed to codemirror-vim as a non-recursive mapping in its mode, with `<Leader>` already resolved by our parser, so one vimrc drives both editors.
- **ADR-071 Accounts live in the sidebar, and groups of them have registers.** As in Actual, the sidebar lists 所有帳戶, 預算內 and 追蹤 with their accounts and balances; each opens a register, and a budget opens on 所有帳戶 (until the budget page of M6). A group's register (`GET /budgets/{id}/register?scope=all|onBudget|offBudget`, routes `/accounts/all`, `/accounts/on-budget`, `/accounts/off-budget`) shows one row per transaction and account of the group it has entries on, with an account column; a transfer between two accounts of the group is on two rows. Rows are keyed by transaction and account, and every row of a transaction is rebuilt from the one being edited, so the two sides never disagree; `:w` sends each transaction once and `dd` deletes all its rows. New rows start on the account of the row under the cursor, and the account cell moves a row to another account. Drafts moved to version 3.
- **ADR-072 Moving between panes is Vim's window commands, bound by the user.** Elements marked `data-pane` (the sidebar, the page, the register, the split window) are panes; `<C-w>h/j/k/l` and `:wincmd h` move focus to the pane in that direction that had focus last, back to where focus was in it. Nothing is bound by default, and the browser keeps the real Ctrl-w (it closes the tab), so the commands are reached through the user's mappings, the usual vimrc idiom `nnoremap <C-h> <C-w>h` (ADR-070). Editors (`data-editor`) apply mappings themselves; elsewhere (the sidebar, settings pages) a one-key normal-mode mapping to a window command applies too. Fields, open dialogs and menus keep their keys. In the sidebar j/k move between links and Enter opens one. While the split window is open the register above it only moves; its changes wait until the split is closed.
- **ADR-073 Visual mode selects whole rows.** `V` (and `v`, since a row is the unit) starts Vim's linewise visual mode in the register; motions and counts extend the selection, `o` jumps to its other end, `gv` brings back the last one, and Shift-click selects from the cursor. On a selection `d` deletes, `y` yanks, `x` toggles cleared and `c` opens one cell editor whose text goes into the cursor's column of every selected transaction (Enter applies, even empty; Esc with nothing typed cancels). Operators work per transaction, not per row, so a transfer shown twice is changed once; rows that cannot take the change (deleted, opening balance, a split's amount or category) are skipped and counted in the message. Each operation is one undo step, `.` repeats `d` and `x` over as many rows, and `yy`/`dd`/`x` take counts. Deleting or clearing marks all rows when any is unmarked and unmarks them when all are marked. Visual mode has its own mappings, as in Vim: `vnoremap`/`xnoremap` (`noremap` is normal and visual). No multi-transaction split, and no system clipboard.
- **ADR-074 Keys are listed under `?`; focus is a kraft tint.** The register's hint line keeps only the basics (hjkl, i, o, x, :w) and `?` opens the full key reference, with the user's own mappings, in the register and the split window alike. The register fills its width: payee, note and category share the room beyond their minimum widths (the split window's text columns do the same). Where keyboard focus is shown it is a kraft tint, as a visual selection is, never a ring around a whole region: the register has no focus ring, and its cell cursor dims while focus is elsewhere; a focused sidebar link is tinted while the current one keeps its kraft bar; the completion list's picked option is tinted with a bar and scrolls into view. Ctrl-n cannot be used in Chrome (the browser keeps it for a new window), so completion also takes the arrows, and users map other keys to `<C-n>`/`<C-p>` (`inoremap <C-j> <C-n>`); a completion picked with the keys is kept by Enter and by Esc, even before anything is typed.
- **ADR-075 Mappings can be limited to a pane with `autocmd FileType`.** As Vim users map keys for netrw (`autocmd FileType netrw nmap <buffer> l <CR>`), `autocmd FileType sidebar nnoremap l <CR>` maps `l` only in the sidebar; the file types are the pane names of ADR-072 (`sidebar`, `register`, `split`, `main` for other pages), several separated by commas. Other autocmd events are not supported; `<buffer>` is accepted and changes nothing. In a pane its own mappings win over global ones of the same keys. The sidebar now reads keys through the mappings too (j/k, gg/G, Enter opens a link, `<C-w>` moves), so it is marked `data-editor` and the page-wide layer of ADR-072 is left with pane `main`. The register also opens with its cursor on the first column (the date) rather than the payee; a new row in a group register starts by asking for its account (the row's account offered), in a single account's register on the payee, and Esc before anything is typed or picked in a new blank row removes it, leaving no undo step; and the interface calls key mappings 快捷鍵 (自訂快捷鍵 for the user's own).
- **ADR-076 Lua configuration, later** *(planned)*. The editor settings may one day also be written in Lua, for users whose Neovim is configured in Lua and for what a vimrc cannot do (loops, functions, user commands, rules, reports). Lua runs in the viewer's browser in a Lua VM (wasmoon) inside a Web Worker, with a time limit and no DOM, network or storage; it sees the ledger only through a read-only `factual.*` API, so a script shared through a budget cannot act for the person running it. It implements a Neovim-flavoured subset (`vim.keymap.set`, `vim.g.mapleader`, `vim.api.nvim_create_autocmd('FileType', ...)` for panes), not Neovim (`require`, `vim.fn` and plugins are not offered), and its mappings land in the same `Keymap` the vimrc parser produces (ADR-070), so the editors do not change. Charts are declared by scripts (`factual.chart{ kind, series, x, y }`) and drawn by the app, so they follow the theme. The `factual.*` API is versioned once released. Until this is taken up (Phase 5) the settings stay vimrc-style.
